# 分阶段实操与参考答案

本项目提供可运行教学底座。下面需要你亲自操作并记录；代码存在、自动化通过和你本人掌握，是不同的证据。

## 第一次练习（约45—60分钟，自行按节奏调整）

1. 双击根目录start.cmd。页面出现后确认“模拟数据”标签、截至日2026-10-10、56行成熟记录。
2. 在总览看四个计划。先不用诊断功能，写下你认为需要关注的计划与理由。
3. 下载CSV样例，任选一行，用Excel手算CTR、CPA、ROAS；再按计划汇总并核对SQL结果。
4. 运行诊断，对每个提示写两个可能原因；不要把提示标题直接当作已经查明的原因。
5. 进入SQL练习，执行四个示例。修改一个字段或排序条件，并解释结果变化。
6. 生成创意草稿，填写并下载实验记录。明确只改变哪个变量、主指标是什么、何时检查。
7. 下载诊断报告，用五句话讲清：业务目标、异常证据、两个假设、下一步验证、当前局限。

验收：能自己复现指标；能解释一个错误计算；能讲清一条诊断并设计验证。

## 阶段A：指标与口径

任务A1：手算独立算例。广告费1000元、曝光100000、点击1000、购买20、收入4000、商品成本2000。
答案：CTR 1%，CVR 2%，CPC 1元，CPM 10元，CPA 50元，ROAS 4倍，贡献利润1000元，项目ROI 33.33%。

任务A2：解释为什么总CTR不能取各行CTR的平均值。用100曝光10点击与10000曝光100点击复现。
答案：总CTR为110/10100≈1.09%；简单平均得到5.5%，忽略了曝光权重。

任务A3：把截至日改为2026-09-27并刷新。
答案：仅2026-09-19的4行满足完整观察窗口，其余52行排除；诊断提示样本日期不足。改回2026-10-10后恢复56行。

任务A4：将样例一行的购买、收入、商品成本设为0，作为新文件导入；观察该行CPA的SQL结果。先保持漏斗关系及口径字段正确。
验收：该行CPA为null/“—”，不是0；说明0元CPA与不可计算的差别。

## 阶段B：SQL与埋点

先学SELECT/FROM/WHERE，再学GROUP BY/SUM/COUNT/CASE WHEN，随后练JOIN、WITH、ROW_NUMBER/LAG。页面提供四条可修改查询。

任务B1：按计划算CPA，并按成本倒序排列。说明哪些字段是分组维度，哪些是汇总数量。
任务B2：JOIN datasets与ad_daily。说明为什么一个数据集对应多行明细，以及为什么重复连接可能放大统计量。
任务B3：运行诊断两次，再执行“埋点：诊断成功、失败与未结束”。查询统计本地练习任务，不代表真实广告任务或用户数。
任务B4：故意输入SELECT unknown_column FROM ad_daily。观察报错，再查product_events中的sql_finished及outcome。
任务B5：把“每日花费变化”查询改成某个计划；增加WHERE campaign_id='B'，但保留dataset_id筛选，核对LAG含义。

验收：能独立完成一次分组与一次关联；能解释WHERE、JOIN、分母、null以及重复数据的影响。

## 阶段C：案例诊断

固定样例的参考信号：B计划CTR约1.20%下降至0.48%；C计划到达率约90%下降至40%；D计划CPM从20元上升至38元。B计划后7天还会出现略负的贡献利润。A计划未触发当前异常规则。

这是生成器刻意构造的变化，说明程序能识别相应信号；不构成真实市场表现。规则只看到指标，无法独立证明素材疲劳、页面故障或竞争加剧。

任务C1：为B计划写出“素材变化”和“受众/版位变化”两个解释，列出需要的附加数据。
任务C2：为C计划设计一次页面与事件排查；说明怎么区分真实到达下降和埋点漏报。
任务C3：解释为什么只看到D计划CPM上升，不应立即建议提高预算。
任务C4：比较全14天与后7天利润。解释总体仍盈利为何可能掩盖近期问题。

验收：每条建议包含证据、假设、核实动作、预期观测和局限。

## 阶段D：创意与实验

任选一份模板草稿，修改表达但保留设定商品事实。写一页实验卡：目标用户、商品事实、变量、对照/实验版本、主要指标、辅助指标、观察窗、样本要求、异常停止条件。

示例：只改变视频首句；其他主要条件保持可比。主指标购买CPA，辅助观察CTR、到达率和CVR。等完整归因窗口后比较；检查样本和分流可比性，预先约定判断方式。可以先离线让受试者判断信息是否清楚；离线偏好不能证明真实广告转化提升。

本项目没有实施随机分流，也没有真实流量，因此当前不能宣称完成A/B投放实验。你可以先完成实验设计，再找真实任务反馈。

## 阶段E：Skill与MCP

阅读项目内.agents/skills/ad-diagnosis/SKILL.md。先用CLI执行：

```powershell
python cli.py datasets
python cli.py diagnose
```

查看mcp_server.py的五个工具。MCP可通过标准输入输出启动：

```powershell
python mcp_server.py
```

它等待JSON-RPC消息，直接运行后暂时没有文字输出是正常的。单独测试已包含在unittest中。接入支持stdio的AI客户端时，命令为Python绝对路径，参数为mcp_server.py绝对路径；本次没有改动你的客户端配置。

实际接入后练习：“先列出模拟数据集，分析截至2026-10-10的异常，给出证据、两个解释和验证步骤。”检查AI是否先读数据、是否保留模拟性质、是否误改数字、是否引用返回来源。把工具调用与回答保存，才可作为真实Agent联调证据。

## 把完整产品过程亲自走一遍

| 环节 | 为什么做 | 你需要操作什么 | 完成标准 |
|---|---|---|---|
| 明确用户 | 避免围着技术堆功能 | 读PRD，选“初级投手”或“客户支持”一个主角色，写下他一次具体任务 | 说明输入、触发时机、困难和预期输出；没有访谈时注明假设 |
| 问题假设 | 让需求能够被证伪 | 写三条假设，例如“缺归因窗提示会误判近期效果”及所需验证资料 | 每条都有可观察结果，能说明什么结果会否定假设 |
| 需求拆解 | 控制第一版范围 | 排列导入、口径、报表、解释、创意的优先级 | 每项有用户故事和验收条件；能说明为何先做 |
| 简要PRD | 对齐输入输出与边界 | 在docs/prd.md副本补上自己的用户和优先级选择 | PRD与实际Demo一致，未来功能与已实现功能分开 |
| 开发Demo | 把规则变成可重复行为 | 顺着app.py→lab.py→SQL读一次请求，修改一个明确需求并保存差异 | 能说明所改函数的输入、输出、失败情况，页面行为符合预期 |
| 测试 | 证明功能在正常与异常输入下成立 | 运行tests；再手测重复导入、0购买、日期不满，写预期与实际 | 正确案例通过，错误能解释；自己的改动有对应复核 |
| 分析结果 | 从数字形成有依据的判断 | 完成阶段C，写一页证据、两个假设和验证动作 | 不把异常等同原因，不把模拟效果当业务成果 |
| 提出迭代 | 验证下一步是否值得做 | 选择一个失败或信息缺口，提出最小改动和再次验收方式 | 有优先理由、验收条件与放弃条件 |

开发切入示例：新增“错误类型说明”而不是再加一个大模型按钮。先在本地复现SQL字段不存在，查看事件中现有error_type；设计结构化分类、修改服务端结果、加测试，再在界面说明怎么修复。是否值得继续，取决于同样任务是否更容易正确完成。

## 虚拟预算练习

本案例设定14天总虚拟预算30,000元，固定样例计算花费25,667.60元，占预算约85.56%，未使用虚拟预算4,332.40元。预算只是教学场景设定；程序没有真实充值、扣款或自动调预算功能。

思考：没花完预算是否一定失败？答案取决于业务目标、可承受CPA和真实需求。如果继续花费只能带来亏损订单，预算完成率不应成为唯一目标。先检查价格、转化、毛利与数据质量，再设计下一轮方案。
